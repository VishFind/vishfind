================================================================================
1. ЧТО ЭТО ЗА ПРОЕКТ
================================================================================

iSearch — сервис поиска редкой и винтажной одежды.

Пользователь описывает вещь текстом и/или прикладывает фото.
Сервер выделяет критерии (тип, цвет, размер, бюджет, бренд и другие признаки)
и отдаёт ссылки на поиск площадок. Сайт сам не является магазином.

Жёсткие правила проекта (их нельзя нарушать):
- Стек остаётся Node.js. Не переписывать на другой язык и не добавлять npm-пакеты без явной просьбы.
- Бюджет разработки 0: не подключать платные API и не предлагать платное без явного предупреждения.
- Секреты только в файле .env. Файл .env не коммитить и не вставлять в чат.
- Не выдумывать цены, наличие и товары. Мы не парсим витрины.
- Неудачный разбор фото не подменять фиктивным успехом.
- Бренд и название модели заполнять только если они читаются на фото (логотип или надпись). Не угадывать по силуэту.
- Точную модель из каталога по фото без читаемой маркировки обещать нельзя.
- Не обходить защиту сайтов и не скрейпить маркетплейсы.

Тон интерфейса: официальный сайт сервиса. Не использовать подачу в духе «увидел в ТикТоке» и заголовок «вещь, которую не гуглится». Текущий заголовок: «Поиск редкой и винтажной одежды».

================================================================================
2. КАК УСТРОЕН КОД
================================================================================

Один процесс Node.js (нужен Node 18+). Зависимостей нет: npm start запускает node server.js.

Поток текстового поиска (нейросеть НЕ участвует):
1. Браузер (js/search.js) шлёт POST /api/search с JSON { query }.
2. server.js вызывает lib/parse-query.js: правила и словари (data/brands.json, movies.json).
3. Из полей собирается поисковая фраза.
4. providers/links.js строит URL по шаблонам из data/sources.json.
5. Ответ: parsed (критерии), sources (ссылки), prices: null.

Площадки (ссылки, не парсинг):
- Ozon: https://www.ozon.ru/search/?text={q}
- Wildberries: https://www.wildberries.ru/catalog/0/search.aspx?search={q}
- Яндекс Маркет: https://market.yandex.ru/search?text={q} (фильтр цены, если подтверждён в sources.json)
- Avito, Lamoda, Zara, eBay — шаблоны в data/sources.json

Текст пользователя важнее догадок модели: бюджет, размер и цвет из текста перекрывают предположения фото.

Интерфейс:
- index.html — поиск
- about.html — зачем проект, что умеет и чего не делает
- contacts.html — почта-заглушка YOUR_EMAIL@example.com, её нужно заменить перед публикацией
- css/site.css — светлая и тёмная тема (js/theme.js, localStorage isearch-theme)
- В выдаче сразу блок «Критерии запроса»: категория, цвет, размер, бюджет, бренд, фильм/образ, фраза, кнопка «Копировать фразу»
- Ниже правка полей и кнопка «Искать снова» (повтор без нового текста, attributes_priority)
- Если было фото — детальный разбор полей модели

Сервер слушает process.env.PORT (по умолчанию 3000) и HOST (по умолчанию 0.0.0.0).
Локально часто запускали на порту 3001, потому что 3000 был занят.

Безопасность без новых библиотек:
- Заголовки: nosniff, X-Frame-Options DENY, Referrer-Policy, CSP (нужен unsafe-inline из-за скрипта темы в HTML)
- Лимит тела: без AI ~64 КБ, с AI ~9 МБ
- Частота: около 20 запросов /api/search в минуту с одного IP (lib/rate-limit.js, счётчик в памяти)
- Статика не отдаёт .env, server.js, data/, lib/, providers/, scripts/, test/

API:
- GET /api/health — статус. Если AI выключен, Ollama не вызывается.
- POST /api/search — основной поиск.
- POST /api/find — старый путь, при AI_ENABLED=false отвечает отказом и просит /api/search.

3. КАК ПОДКЛЮЧЕНА НЕЙРОСЕТЬ (OLLAMA)
================================================================================

Нейросеть нужна ТОЛЬКО для фото. Текстовый поиск работает без неё.

Выбранная модель: qwen3-vl:4b-instruct (библиотека Ollama, ~3.3 ГБ, вход Text+Image).
Железо владельца: AMD Ryzen 5 7500F, NVIDIA GeForce RTX 4060 Ti.
Почему не 2b: qwen3-vl:2b без суффикса -instruct часто кладёт ответ в поле thinking, а content оставляет пустым. Нужен тег *-instruct.
Почему не 8b/30b сразу: 4b — следующий шаг качества, который реально помещается на эту карту. 8b (6.1 ГБ) впритык на 8 ГБ VRAM. 30b/32b не брать.

Схема подключения (ничего не уходит в платное облако):

1. На компьютере запущена программа Ollama. Она слушает http://127.0.0.1:11434
2. Модель скачана командой: ollama pull qwen3-vl:4b-instruct
3. В .env:
   AI_ENABLED=true
   OLLAMA_URL=http://127.0.0.1:11434
   OLLAMA_MODEL=qwen3-vl:4b-instruct
   PHOTO_TIMEOUT_SEC=90
   PHOTO_PIPELINE=schema
4. Фронтенд при загрузке читает GET /api/health.
   Если ai_enabled=true, показывает кнопку «Фото». Иначе прячет её.
5. Пользователь выбирает файл. js/search.js сжимает его на клиенте:
   длинная сторона не больше 1024 px, JPEG quality 0.82, форматы jpg/png/webp/gif, исходник до 8 МБ.
6. По кнопке «Искать» браузер шлёт POST /api/search:
   { query, image: "data:image/jpeg;base64,...." }
   Таймаут ожидания на клиенте для фото ~100 секунд, для текста ~30.
7. server.js срезает префикс data:image/...;base64, и вызывает функцию analyze().
8. analyze() делает HTTP POST на {OLLAMA_URL}/api/chat.
   Тело примерно такое:
   {
     model: "qwen3-vl:4b-instruct",
     messages: [{ role: "user", content: "<промпт>", images: ["<чистый base64>"] }],
     stream: false,
     format: <JSON Schema PHOTO_FORMAT>,
     think: false,
     options: { temperature: 0, num_predict: 900 },
     keep_alive: "30m"
   }
9. Ollama обязана вернуть JSON по схеме. Поля:
   garment_type, subtype, color_primary, color_extra[], material, pattern,
   collar, closure, pockets, length, fit, hardware_and_details, era_or_style,
   visible_text[], brand, model_name, description.
10. Сервер чистит мусор («не указано», строка "null", догадки бренда),
    слегка переводит частые английские ярлыки (jacket→куртка, red→красный),
    сливает поля в общий parsed. Текст пользователя побеждает пустые поля модели.
11. Если JSON невалидный — один повтор со строгим промптом.
    Если одежды нет или разбор сорвался — HTTP 502 с честной ошибкой, photo_used=false.
    Таймаут одного вызова — 90 секунд (AbortController).
12. Дальше та же сборка ссылок, что и для текста.

Два режима разбора (переменная PHOTO_PIPELINE):
- schema — один проход сразу в JSON Schema. Выбран по умолчанию после сравнения.
- twopass — сначала свободное описание по картинке, потом второй вызов без картинки превращает текст в JSON.
- auto — schema, и если полей мало, пробует twopass и берёт более полный.

Сравнение на qwen3-vl:4b-instruct (скрипт scripts/compare-photo-pipelines.js):
schema давал больше заполненных полей, чем twopass. Поэтому в .env.example стоит PHOTO_PIPELINE=schema.
На очень простом тестовом фото (красная картинка с надписью JACKET) модель честно не выдумывает материал и подтип; visible_text = ["JACKET"]. Это нормально.

Проверка, что Ollama жива:
- ollama list  — модель должна быть в списке
- GET /api/health при AI_ENABLED=true возвращает ollama, model, model_installed

4. КАК ПОДКЛЮЧИТЬ ДРУГУЮ НЕЙРОСЕТЬ
================================================================================

Вариант А. Другая модель внутри той же Ollama (самый простой)

1. Посмотреть официальный каталог: https://ollama.com/library
   Нужна модель с входом Image (vision), лучше тег *-instruct, не thinking-версия для JSON.
2. Прикинуть память: размер скачивания плюс 1–2 ГБ на картинку и контекст.
   На RTX 4060 Ti разумно: qwen3-vl:4b-instruct (сейчас) или qwen3-vl:8b-instruct, если VRAM 8–16 ГБ и можно подождать дольше.
   Минимум для OCR бирок: minicpm-v4.5 (~6 ГБ), но её надо отдельно сравнивать по качеству.
3. Скачать самому (ассистент не качает без согласия):
   ollama pull ИМЯ_МОДЕЛИ
4. В .env заменить одну строку:
   OLLAMA_MODEL=ИМЯ_МОДЕЛИ
5. Перезапустить node server.js.
6. Прогнать то же фото через POST /api/search и через:
   node scripts/compare-photo-pipelines.js
   (в скрипте модель берётся из OLLAMA_MODEL).
7. Если новая модель не принимает format=JSON Schema (ответ 400), код уже откатывается на format: "json".
   Если content пустой, а текст в thinking — это thinking-модель, её не использовать или оставить extractModelText как запасной путь.
8. Промпт и схему менять в server.js: PHOTO_FORMAT, buildPhotoPrompt, parsePhotoFields.
   Не ослаблять правило: brand и model_name только если видны.

Вариант Б. Другой локальный сервер с похожим API (LM Studio, llama.cpp server, vLLM)

Идея та же: картинка base64 + строгий JSON.
Менять только функцию ollamaChat() в server.js и переменную OLLAMA_URL.
Контракт, который должен сохраниться:
- на вход: промпт, массив картинок base64, temperature 0, JSON Schema или mode json, таймаут 90 с
- на выход: строка JSON с теми же полями PHOTO_FORMAT
- при ошибке, таймауте или пустом ответе — бросать исключение, не подставлять выдуманный разбор

Если API не умеет поле images внутри messages, адаптировать формат тела запроса в одном месте (ollamaChat / analyzeSchema), фронтенд не трогать.

Вариант В. Облачная модель (OpenAI, Gemini и т.п.)

Это уже платно или с лимитами. Подключать только после явного согласия владельца.
Ключ класть в .env (например VISION_API_KEY), не во frontend.
Заменить вызов в analyze() на HTTPS к API провайдера.
Картинку по-прежнему слать с нашего сервера, не из браузера напрямую (чтобы ключ не светился).
Схему полей, запрет угадывать бренд и честный 502 оставить.
На бесплатном хостинге без своего GPU локальная Ollama обычно недоступна: для публичной версии ставить AI_ENABLED=false, пока нет отдельного места, где крутится модель.

Чего не делать при смене модели:
- не скрейпить магазины «чтобы модель знала каталог»
- не обещать точный артикул
- не повышать temperature выше 0 для разбора фото
- не выключать повтор при битом JSON и честную ошибку
