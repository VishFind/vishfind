# AMVERA_DEPLOYMENT.md — Инструкция по деплою и эксплуатации VishFind в Amvera Cloud

> Версия документа: 1.0.
> Назначение: практическое руководство для работы с проектом VishFind на хостинге Amvera Cloud.
> Важно: документ описывает **актуальную конфигурацию** (файл [`amvera.yml`](amvera.yml:1)). Если в старых заметках указаны другие значения (`run.scriptName: server.js`, `containerPort: 3000`) — фактический файл использует `command: npm run start` и `containerPort: "80"`; расхождения помечены ниже.

---

## 1. Что такое Amvera в этом проекте

- **Amvera Cloud** — платформа, которая собирает и запускает проект VishFind из GitHub-репозитория (ветка `main`) и отдаёт его по HTTPS.
- **Amvera НЕ запускает локальную Ollama разработчика.** Контейнер работает в изолированном окружении и не имеет доступа к `127.0.0.1` компьютера разработчика.
- Поэтому в Amvera `AI_ENABLED=false`: кнопка «Фото» и Ollama-разбор выключены, работает текстовый поиск и ссылки (`links:on`).
- Для работы AI в облаке в будущем понадобится **отдельный AI-сервер** (VPS с Ollama, доступный по HTTPS с авторизацией) **или облачная vision-модель по API**. Это отдельный этап, сейчас не подключён.

## 3. Чек-лист переменных окружения

Задаются в панели Amvera (раздел «Переменные окружения» проекта `vishfind`). Никогда не кладите секреты в код/репозиторий — только сюда.

| Переменная | Рекомендуемое значение для демо | Когда менять |
|---|---|---|
| `NODE_ENV` | `production` | всегда в Amvera |
| `PORT` | `3000` (если Amvera не задаёт порт сама — см. важное ниже) | выставить равным ожидаемому порту контейнера |
| `HOST` | `0.0.0.0` | по умолчанию так и есть; менять не нужно |
| `LOG_LEVEL` | `info` | `warn` — если шум; `debug` — только временно для отладки |
| `TRUST_PROXY` | `true` | ставить `true` за прокси Amvera; `false` — если прямого доступа к контейнеру |
| `AI_ENABLED` | `false` | только когда Ollama вынесена на отдельный доступный сервер |
| `WEB_SEARCH_ENABLED` | `false` | только когда веб-поиск реально включён и есть ключ |
| `OLLAMA_URL` | пусто (или локальный адрес только для dev) | включать только при реальном внешнем Ollama |
| `OLLAMA_MODEL` | `qwen3-vl:4b-instruct` | при включении AI |
| `PHOTO_TIMEOUT_SEC` | `90` | при включении AI |
| `PHOTO_PIPELINE` | `schema` | при включении AI |
| `EBAY_CLIENT_ID` / `EBAY_CLIENT_SECRET` | пусто | когда получен доступ к eBay Browse API |

> **Важно о `PORT`:** в текущем [`amvera.yml`](amvera.yml:1) `containerPort: "80"` — платформа ожидает приложение на 80-м порту контейнера; приложение по умолчанию слушает 3000. Если Amvera не инжектит `PORT=80` автоматически, задайте `PORT=80` в переменных, иначе трафик может не доходить (502/«сайт не отвечает»). Решение сверьте с логом запуска (шаг 6.13).

| Переменная | Зачем нужна | Если не задать | Безопасные значения |
|---|---|---|---|
| `NODE_ENV` | включает prod-ветки конфигурации ([`lib/config.js`](lib/config.js:1)): `AI_ENABLED=false`, `LOG_LEVEL=warn`, `TRUST_PROXY=true` по умолчанию, лимит тела 64 КБ | применится дефолт `development` (AI_ENABLED=true и лимит ~9 МБ — нежелательно для прода) | `production` |
| `PORT` | порт HTTP, который слушает сервер | сервер слушает 3000 — может не совпасть с портом платформы | `3000` или `80` (по факту платформы) |
| `HOST` | адрес bind | по умолчанию `0.0.0.0` — слушает все интерфейсы (нужно для контейнера) | `0.0.0.0` |
| `LOG_LEVEL` | уровень логов: `error` < `warn` < `info` < `debug` | по умолчанию в prod `warn` (ошибки видны, шаг запуска — нет) | `info` для рабочего режима |
| `TRUST_PROXY` | доверять `X-Forwarded-For` для определения IP клиента | `false` → rate limit видит внутренний IP прокси (все пользователи = один «IP») | `true` за прокси, `false` без прокси |
| `AI_ENABLED` | включает фотоанализ через Ollama | `true` в облаке → сервер будет пытаться ходить на `127.0.0.1:11434` и получать ошибки | `false` |
| `WEB_SEARCH_ENABLED` | платный веб-поиск (Tavily/Ollama Web) | `false` → веб-поиск выключен | `false` |
| `OLLAMA_*` | параметры локальной модели | без них фото-путь не работает (и правильно: он выключен в облаке) | только для dev |
| `EBAY_CLIENT_ID` / `EBAY_CLIENT_SECRET` | реальные предложения eBay | без ключей — демо-предложения и фолбэк | пусто, пока нет доступа |

> **Внимание:** текущий парсер булевых значений в [`lib/config.js`](lib/config.js:1) принимает **только `true`/`false`** (без учёта регистра). Значения вроде `1`, `yes`, `on` НЕ распознаются и дадут дефолт. Для `TRUST_PROXY`/`AI_ENABLED`/`WEB_SEARCH_ENABLED` используйте именно `true`/`false`.

## 4. Рекомендации по NODE_ENV, TRUST_PROXY и LOG_LEVEL

### 4.1. `NODE_ENV=production`

- **Зачем:** включает production-ветки в [`lib/config.js`](lib/config.js:1): `AI_ENABLED=false` (фото выключено в облаке), `LOG_LEVEL=warn` по умолчанию, `TRUST_PROXY=true`, лимит тела 64 КБ. Также стандартное поведение Node-библиотек (кэширование, строгость ошибок) зависит от `NODE_ENV`.
- **Влияние:** правильные дефолты + меньше шансов включить тяжёлые dev-режимы в проде.
- **Почему задавать в Amvera:** платформа не всегда проставляет `NODE_ENV` сама; без него сервер может работать в dev-режиме.
- **Когда менять:** не менять. В Amvera всегда `production`.

### 4.2. `TRUST_PROXY=true`

- **Что такое reverse proxy:** промежуточный сервер, который принимает запросы от пользователей и передаёт их приложению, подставляя настоящий IP клиента в заголовок `X-Forwarded-For`.
- **Почему Amvera использует прокси:** платформа маршрутизирует внешний трафик через свой слой; приложение видит соединения от прокси, а не от пользователей.
- **Когда нужен:** когда приложение стоит за таким прокси (стандартный кейс Amvera) — `TRUST_PROXY=true`.
- **Влияние на определение IP:** при `true` сервер берёт первый адрес из `X-Forwarded-For` (настоящий IP клиента), при `false` — `socket.remoteAddress` (IP прокси).
- **Почему важно для rate limit:** иначе все пользователи будут учтены за одним внутренним IP прокси, и общий лимит 20 запросов/мин исчерпается мгновенно (сайт начнёт отдавать 429 всем).
- **Когда НЕ ставить:** если приложение доступно без внешнего прокси (например, прямая публикация порта) — тогда заголовок можно подделать, и доверять ему нельзя.

### 4.3. `LOG_LEVEL`

- **Уровни:** `error` (только ошибки) → `warn` (ошибки + предупреждения) → `info` (+ события запуска и важные шаги) → `debug` (все детали).
- **Почему для Amvera по умолчанию нужен `info`:** видно, что сервер запустился, какой порт слушает, какие провайдеры активны; при этом шума меньше, чем в `debug`.
- **Когда включать `debug`:** при разборе конкретной проблемы (например, ошибок eBay или фото) — временно.
- **Почему `debug` не навсегда в production:** много шума, рост потребления логов, и вероятность случайно залогировать лишние детали выше (хотя санитизация всё равно работает).
- **Как логи помогают:** по строке `VishFind запущен` видно старт; по `rate limit exceeded` — перегрузку/атаку; по `eBay search failed` — деградацию eBay; по `uncaughtException` — баг.

## 5. Health-check

**URL:** `GET /api/health` — например, `https://<домен-amvera>/api/health`.

**Что делать:** открыть URL в браузере или `curl`:
```
curl https://<домен-amvera>/api/health
```

### Текущий (актуальный) формат ответа

Демо без AI (production):

```json
{
  "ok": true,
  "name": "vishfind",
  "version": "1.0.0",
  "env": "production",
  "uptime_sec": 42,
  "timestamp": "2026-10-26T15:00:00.000Z",
  "ai_enabled": false,
  "web_search": null,
  "providers": [
    { "id": "links", "enabled": true },
    { "id": "websearch", "enabled": false }
  ],
  "ebay": {
    "configured": false,
    "circuit_open": false,
    "fails": 0,
    "threshold": 3,
    "last_success_at": null,
    "last_error_at": null,
    "last_check_at": null
  },
  "message": "AI выключен. Работает текстовый поиск /api/search."
}
```

Локальный режим с AI (`AI_ENABLED=true`): ответ будет тем же по структуре, но `"ai_enabled": true` и `"message": "AI включён (локальная разработка). Работает текстовый поиск /api/search."`

### Как понимать поля

| Поле | Что означает | Как понять состояние AI/Ollama |
|---|---|---|
| `ok` | сервис жив | `true` — можно использовать как health-check платформы |
| `ai_enabled` | включён ли фото-путь | `false` — AI выключен (норма для Amvera); `true` — включён |
| `env` | `production` / `development` | в Amvera должно быть `production` |
| `web_search` | провайдер веб-поиска или `null` | `null` — выключен (норма) |
| `providers` | состояния провайдеров | `links:enabled:true` — ссылки работают |
| `ebay` | состояние eBay-провайдера | `configured:false` — ключей нет; `circuit_open` — временная пауза |

**Ответы на типовые вопросы:**

- **`ai_enabled=false`** — кнопка «Фото» скрыта, фото-запросы возвращают 503 с подсказкой. Это ожидаемо для Amvera. Для включения нужен внешний сервер Ollama (этап V3).
- **Как понять, что Ollama доступна / модель установлена:** текущий `/api/health` **намеренно не проверяет Ollama** (health должен быть мгновенным и не падать из-за внешних сервисов; прежние поля `ollama`/`model`/`modelInstalled` из ранней демо-версии убраны). Проверка Ollama — только локально: `ollama list` (модель `qwen3-vl:4b-instruct` в списке) и диагностический запрос `GET http://127.0.0.1:11434/api/tags`.
- **`ollama=false` / `modelInstalled=false`** — такие поля в текущем ответе отсутствуют; их наличие в старых примерах относится к демо-версии. Локальная проверка доступности Ollama — командой `ollama list` и обращением к `/api/tags` на `127.0.0.1:11434`.

## 6. Чек-лист деплоя в Amvera

1. Проверить, что код **закоммичен** и запушен в ветку `main` GitHub (`git status` → чисто, `git push origin main`).
2. Проверить, что [`amvera.yml`](amvera.yml:1) находится **в корне репозитория**.
3. Проверить [`package.json`](package.json:1): есть скрипт `start` (`node server.js`), `engines.node >= 18`, нет случайных зависимостей.
4. Проверить, что **нет `.env` в Git** (он в `.gitignore`); сервер защищает `/.env` → 403.
5. Проверить переменные окружения проекта в панели Amvera (раздел 3).
6. `NODE_ENV=production`.
7. `LOG_LEVEL=info` (или `warn`, если шум).
8. Решить, нужен ли `TRUST_PROXY=true` (нужен — Amvera использует прокси).
9. Нажать «Сборку» / запустить деплой (Amvera соберёт из ветки `main`).
10. Открыть **лог сборки** (раздел 7) и убедиться, что `npm install` завершился без ошибок.
11. Убедиться, что нет ошибок `npm install` (в проекте нет зависимостей — сборка должна быть успешной).
12. Открыть **лог приложения** и убедиться в строке старта.
13. Убедиться, что сервер запустился на `0.0.0.0`: строка вида `VishFind запущен: http://localhost:{PORT} (bind 0.0.0.0)`. Сверить `{PORT}` с ожидаемым портом Amvera (см. важное о `PORT` в разделе 3 — при необходимости выставить `PORT=80`).
14. Проверить `GET /api/health` через публичный URL: `ok: true`, `env: production`.
15. Проверить главную страницу: поиск по тексту возвращает ссылки и предложения.
16. Проверить мобильную версию (режим телефона в DevTools).
17. Создать/привязать домен Amvera (если нужно; пока используется бесплатный домен).
18. Проверить HTTPS: сайт открывается по `https://`.

## 7. Как читать логи Amvera

В панели Amvera три вида логов:

| Лог | Что показывает | Когда смотреть |
|---|---|---|
| **Лог сборки** (build) | команды `npm install`, скачивание, копирование артефактов, успех/ошибка сборки | сразу после деплоя, если приложение не появилось |
| **Лог приложения** (runtime/app) | stdout/stderr запущенного процесса (`node server.js`) — логи нашего приложения | при ошибках 502/500, растущем тайминге |
| **Системный лог** | события платформы: перезапуски, остановки, health-проверки | при «самопроизвольных» падениях |

**Нормальные строки (примеры):**
```
added 0 packages in ...                       # npm install успешен (зависимостей нет)
Container builder has completed with exit code: 0
Starting application
VishFind запущен: http://localhost:3000 (bind 0.0.0.0)
```

**Проблемные строки и их смысл:**
```
Cannot find module '...'                     # нет зависимости или опечатка в require
Missing script: "start"                      # в package.json нет скрипта start
Error: listen EADDRINUSE ...                 # порт занят другим процессом
exit code: 1                                # процесс завершился с ошибкой (см. лог выше)
502 ...                                     # шлюз не нашёл работающее приложение
timeout / ETIMEDOUT                         # внешний вызов (Ollama/eBay) не ответил
```

**Про JSON-логи приложения:** наш логгер пишет JSON-строки в stdout: `{"ts": "...", "level": "warn", "msg": "rate limit exceeded", ...}`. Это удобно фильтровать по `level` и словам (`eBay search failed`, `uncaughtException`, `VishFind запущен`).

## 8. Риск `persistenceMount: /data`

- **Что такое `persistenceMount`:** в [`amvera.yml`](amvera.yml:1) указан `persistenceMount: /data` — Amvera монтирует постоянный том (volume) в каталог `/data` контейнера. Данные в нём переживают перезапуски.
- **Зачем нужен `/data`:** для будущей базы данных (PostgreSQL), кэша, загруженных файлов, пользовательских данных. Сейчас код его **не использует**.
- **Какие данные могли бы там храниться:** файлы БД, кэш предложений, метаданные пользователей, модерация (этапы V2+).
- **Почему сейчас проект может не использовать этот путь:** весь каталог проекта лежит в корне контейнера (артефакты `"*"` → `/`), а в репозитории уже есть папка `data/` (JSON-словари). Возможен **конфликт имён**: смонтированный том `/data` может «затенять» репозиторную папку `data/`.
- **Как проверить в логах Amvera, используется ли `/data`:** в логе приложения искать предупреждения вроде `data/sources.json не загружен`, `data/brands.json не загружен`, `data/demo-offers.json не загружен` (логгер пишет их на уровне `warn`). Такие строки = словари не читаются из-за затенения.
- **Какие ошибки возможны при недоступности пути:** сработает fallback: пустые `sources` (ссылки пропадут), пустые демо-предложения (offers станет пустым), пустой словарь брендов. Сервер не падает, но функциональность теряется — поэтому важно проверить логи.
- **Как безопасно проверить запись в `/data`:** временно выставить `LOG_LEVEL=debug` и/или выполнить проверочный скрипт на запись (например, `fs.writeFileSync('/data/.probe', 'ok')`) — но это разовое действие вне текущей задачи (код не меняется без согласования).
- **Почему не хранить секреты в `/data`:** том — не место для ключей: ключи задаются в переменных окружения панели Amvera, чтобы не попадать в репозиторий и легко ротироваться.
- **Почему `/data` не заменяет базу данных:** том — это файловое хранилище, а PostgreSQL даёт транзакции, индексы, конкурентный доступ. На этапе V2 БД будет использовать том `/data` как место для файлов данных.

## 9. Что делать при ошибке деплоя

| Ошибка | Вероятная причина | Что проверить |
|---|---|---|
| `Cannot find module '...'` | нет зависимости или неверный импорт | `package.json` (зависимости), корректность `require(...)` в коде, успешность `npm install` |
| `Missing script "start"` | в `package.json` нет скрипта start | секция `scripts.start` (= `node server.js`) |
| `EADDRINUSE` | порт занят | `PORT` в переменных, `containerPort` в `amvera.yml`, нет ли второго инстанса |
| `502` | приложение не запустилось или упало после старта | лог приложения, строка `VishFind запущен...`, соответствие PORT/containerPort |
| `Timeout` / `ETIMEDOUT` | долгий ответ внешнего сервиса или недоступный Ollama | `OLLAMA_URL` (не должен указывать на localhost в облаке), таймауты, здоровье eBay |
| `403` | rate limit / защита служебных путей / NODE_ENV | `TRUST_PROXY` (правильный IP), лимиты (429 в ответе), не открывать `/.env` и служебные пути |
| `exit code: 1` | процесс завершился с ошибкой | лог приложения целиком: последние строки перед падением |
| Приложение открывается, но пустые ссылки/предложения | затенение `data/` томом `/data` | лог `warn` вида `data/sources.json не загружен` (раздел 8) |

### Общий порядок действий при проблеме

1. Открыть лог сборки → убедиться, что `npm install` успешен.
2. Открыть лог приложения → найти строку запуска и последнюю ошибку.
3. Проверить переменные окружения (раздел 3), особенно `NODE_ENV`, `TRUST_PROXY`, `PORT`.
4. Проверить `GET /api/health` (раздел 5).
5. При необходимости временно выставить `LOG_LEVEL=debug`, перезапустить, изучить логи, вернуть `info`.
6. Не менять код без согласования; амвера-файл и продакшн-конфиг — после подтверждения владельца.
